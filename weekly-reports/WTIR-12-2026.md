## A Note on Data Verification

A number this large warranted scrutiny before being reported. The raw `logstash-*` index returned roughly 19.9 million documents for the reporting window — thirteen times the 1.53 million dashboard total. That gap was fully explained once the index's non-attack document types were excluded: P0f (11.3M, passive OS fingerprinting), Suricata (6.86M, IDS alerts on all traffic, not just honeypot hits), Fatt (218,806, TLS/fingerprint metadata), and NGINX (5,492, reverse-proxy access logs) all share the same index but do not represent attack events. Once filtered to honeypot-specific document types only, the raw counts matched the dashboard figures within rounding for every honeypot checked.

A second concern — apparent duplicate events, where the same source IP, port, and second-level timestamp repeated hundreds of times — was checked directly against the raw documents. In every case, the "duplicates" turned out to be distinct events: a scanning bot hammering a long list of different config-file and credential paths against H0neytr4p within the same one-second window, not the ingestion pipeline double-counting. A raw-log ground-truth check against the week's top single attacker (138.226.239.3, 258,762 hits per the dashboard) against the actual Ciscoasa log file on the sensor returned 259,157 — a 0.15% variance, consistent with ordinary ingestion lag rather than inflation.

**The headline attack counts in this report are honeypot-filtered and independently ground-truthed against raw log files — not raw `logstash-*` totals.** P0f and Suricata data are cited below for OS-fingerprinting and signature context only, never as additional attack volume.

## Methodology

Each profiled IP and its ASN were checked against OSINT sources — AbuseIPDB, VirusTotal, GreyNoise, Shodan, and Hurricane Electric/RIPE WHOIS and RDAP — for abuse history, host fingerprinting, and vendor detection consensus. Every candidate IP and ASN was checked against WTIR-01 through WTIR-11 for recurrence before being written up.

**Confidence tiers**, assigned per finding rather than per IP:

| Tier | Meaning |
|---|---|
| **High** | Directly confirmed by first-hand telemetry (GreyNoise "observed," matching Suricata exploit-classified signatures, RIPE Atlas probe geolocation) or independently corroborated across multiple unrelated sources |
| **Medium** | A plausible, well-supported read of the data, but resting on inference — a shared registrant name, a hostname pattern, a single source's classification |
| **Low** | Suggestive but unverified — a naming convention, a subnet neighbor, a single low-volume signature with no exploit classification |

**Terminology and limitations:** "Attacks" and "events" refer to logged honeypot interactions, not confirmed compromises. A Suricata alert signature with an attached CVE ID means traffic matched a known exploit pattern, not that the exploit succeeded against a real target. GeoIP and registered ownership tell you who administers a network, not who is behind the keyboard.

### Investigation 1 — Two Passports, Round Two: Ghana and Kazakhstan (GSL Networks Pty LTD, AS137409)

**5.180.179.16: 22,295 hits | Rank #7** — **212.116.237.21: 19,201 hits (WTIR-08 comparison only, different ASN)**

*A personal note before this one: Ghana isn't a random pick. My parents were both born and raised there, so when it turned up as a source country this week, it was worth digging into properly.*

![WTIR-12 Ghana Reference Map](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-12/WTIR-12%20Ghana%20Reference%20Map.png)

![WTIR-12 Threat Actor 1 Ghana](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-12/WTIR-12%20Threat%20Actor%201%20Ghana.png)

WTIR-08 documented an operator running the same infrastructure simultaneously tagged Georgia and Kazakhstan, sharing a domain and abuse history. This week produced a second, independent case of the same trick, this time under **GSL Networks Pty LTD (AS137409)** — a legitimate Australian carrier that leases IP space to downstream customers rather than an obvious shell operation itself.

**5.180.179.16** (Ghana-tagged) generated 22,295 hits, almost entirely SSH brute-force via Cowrie. RIPE WHOIS shows the /24 registered to IPLuo BV, a Netherlands LIR, allocated through a prefix broker — leased space, not organically owned infrastructure.

![WTIR-12 Threat Actor 1 Ghana WHOIS](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-12/WTIR-12%20Threat%20Actor%201%20Ghana%20WHOIS.png)

Attribution across sources is scattered: the honeynet and RIPE both say Ghana, AbuseIPDB says Germany, OTX AlienVault says the Netherlands under an entirely different ASN (AS1239), and GreyNoise's own probe traces to Sydney. AbuseIPDB shows 90 reports from 35 distinct sources going back to April 2024 — port scans, SSH brute-force, VoIP fraud, and web-app attacks — and a VirusTotal community comment independently confirms this IP is already tracked by the TSEC T-Pot honeypot network, separate from this one. Talos tags the surrounding content category as "Filter Avoidance" / "Personal VPN," and the 126 neighboring addresses in the block show uniform low-volume activity, consistent with a brokered block possibly doing double duty as commercial VPN exit infrastructure.

**212.116.237.21** (Kazakhstan-tagged) sits under the same ASN, but the registration is a starker case: the registrant is literally named "Private Customer," address "Private Residence," country British Virgin Islands, leased through IPXO — a commercial IP marketplace — with a generic third-party abuse mailbox.

![WTIR-12 Threat Actor 1 Kazakhstan WHOIS](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-12/WTIR-12%20Threat%20Actor%201%20Kazakhstan%20WHOIS.png)

Unlike its Ghana sibling, this address has almost no history: zero AbuseIPDB reports, zero VirusTotal detections, zero OTX pulses, and the block itself was only registered in August 2025.

**Worth being explicit:** this is not the same cluster resurfacing from WTIR-08. That one ran under AS205997 (registrant "Vlad Cojuhari"), a completely different netblock with no relation to GSL Networks.

![WTIR-12 WTIR-08 Kazakhstan Historical Reference](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-12/WTIR-12%20WTIR-08%20Kazakhstan%20Historical%20Reference.png)

**Assessment — Confidence: Medium.** Two brokered/leased netblocks under the same ASN, simultaneously tagged to different countries, both registered with privacy/opaque registration data of limited attribution value — one aged and well-documented, one fresh and clean. This is consistent with a potential rotation strategy in which older, more-reported infrastructure is supplemented or replaced by newly leased addresses, though the data here doesn't establish that as the confirmed reason for the difference. As with WTIR-08, this establishes infrastructure overlap under a shared ASN, not confirmed single-operator attribution.

**Defensive relevance:** Brokered/leased IP space (PREFIXBROKER-MNT, IPXO, and similar marketplaces) is increasingly a feature of scanning infrastructure specifically because it lets operators acquire clean-reputation addresses disconnected from any obvious hosting-provider fingerprint. Blocklisting strategies that key off ASN or hosting-provider reputation alone will miss this category of traffic.

### Investigation 2 — 75.130.77.237 (Charter Communications LLC, AS20115) | Suspected Compromised Residential CPE

**98,299 hits | Rank #3**

Unlike the leased/brokered infrastructure above, this actor is a genuine residential/business subscriber — clean reverse DNS (`syn-075-130-077-237.biz.spectrum.com`), directly allocated by Charter, geolocation (Maryville/Sevierville, Tennessee) agreeing across every source checked.

![WTIR-12 Threat Actor 2 Charter Shodan](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-12/WTIR-12%20Threat%20Actor%202%20Charter%20Shodan.png)

What makes this one notable is a single open port: **TCP 7547, TR-069/CWMP** — the protocol ISPs use to remotely manage a subscriber's router. An open TR-069 port on a residential connection, combined with GreyNoise tags for SSH Bruteforcer, SSH Connection Attempt, and SSH Alternative Port Crawler, is suggestive of a compromised home router acting as a botnet node. TR-069/CWMP exposure is a known attack surface for residential IoT/CPE devices and has been abused by later IoT botnet campaigns, though the original 2016 Mirai worm's primary propagation method was Telnet scanning with default credentials, not TR-069 — the two are related but distinct attack surfaces within the same broader IoT-botnet threat category.

GreyNoise and CINS Army both classify the IP malicious; BitDefender and G-Data flag phishing; several more vendors rate it suspicious (4/90 overall on VirusTotal). OTX AlienVault carries 22 separate pulses for this address, the oldest dating back five years, tagged consistently by many independent honeypot operators for brute-force/scanner activity — modified as recently as minutes before this data was pulled.

**Assessment — Confidence: Medium-High.** A residential CPE device, independently and repeatedly tagged as Mirai-associated brute-force infrastructure across a five-year public history — suggestive of a long-term, low-and-slow compromised botnet node rather than dedicated attacker-owned infrastructure. This assessment rests on exposed attack surface (TR-069), external reputation history, and behavioral tagging; it does not include direct evidence of compromise on this specific device (no observed command execution, malware download, or C2 callback from this address), so "suspected" rather than "confirmed" compromise is the accurate framing.

**Defensive relevance:** TR-069/CWMP interfaces should not be unnecessarily exposed to unrestricted public access; ISP deployments should enforce appropriate access controls and restrict management traffic to authorized ACS infrastructure. Reachability alone isn't proof of misconfiguration — legitimate ACS communication requires it — but the exposure remains a known attack surface that this class of botnet has repeatedly targeted.

Every prior report in this series documented scanning and brute-forcing. The most significant host, **94.154.43.200**, served files named `Sakura.sh` and architecture-specific binaries. Every hash-named file it dropped was pulled and independently verified with `file` and `sha256sum` against the raw honeypot capture before checking any third-party classification.

![WTIR-12 Threat Actor 3 Cowrie Downloads Listing](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-12/WTIR-12%20Threat%20Actor%203%20Cowrie%20Downloads%20Listing.png)
![WTIR-12 Threat Actor 3 File and SHA256 Verification](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-12/WTIR-12%20Threat%20Actor%203%20File%20and%20SHA256%20Verification.png)

SHA-256 `5991ed79238ab8bd0f4c4983e3e6fbc73784396daf7d585349eae37d5907c60b`, downloaded as `x-8.6-.Sakura`, returned 40/58 malicious on VirusTotal, classified **trojan.gafgyt/mirai**.

![WTIR-12 Threat Actor 3 VirusTotal Gafgyt Sakura](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-12/WTIR-12%20Threat%20Actor%203%20VirusTotal%20Gafgyt%20Sakura.png)

VirusTotal's automated code analysis confirms this is a Linux DDoS bot (Mirai/Kaiten derivative) that connects to a C2 server, reports back infected-device metadata, and executes multiple flood attack vectors (Valve Source Engine floods, TCP floods, UDP floods, custom STD/HEX floods) via commands including `STDHEX`, `NFODROP`, `OVHKILL`, `XMAS`, `CRUSH`, `STOMP`, and `STOP`. A hardcoded reference to `dayzddos.co`, a DDoS-for-hire booter service, suggests this is rented infrastructure rather than a bespoke tool. The same build was confirmed across three architectures (x86-64, MIPS, AArch64), consistent with a standard multi-architecture IoT botnet deployment.

**The staging server itself is independently catalogued by abuse.ch's ThreatFox as active botnet C2 infrastructure** — two IOC entries (ports 606 and 80). The artifact chain here is worth being explicit about, since two different files are involved: `Sakura.sh` is the bash loader script served by the staging server (SHA-256 `6a7e1676d52a85906d43a543bdb35f8b3282447a5ce8c98dfad33e04afe79dc6`), which in turn fetches the architecture-specific binary payload, `x-8.6-.Sakura` (SHA-256 `5991ed79...`, the Gafgyt sample analyzed above). **ThreatFox's linked MalwareBazaar sample matches the loader script's hash (`6a7e1676...`), not the binary's** — meaning the loader itself, not the final payload, is the artifact independently confirmed by abuse.ch. This is still third-party confirmation of a file captured directly on this honeynet, independent of this analyst's own tooling, but the confirmation applies specifically to the delivery script rather than the DDoS binary it deploys.

![WTIR-12 Threat Actor 3 AbuseIPDB C2 Host](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-12/WTIR-12%20Threat%20Actor%203%20AbuseIPDB%20C2%20Host.png)

AbuseIPDB shows 189 reports from 102 distinct sources for the staging host, 100% confidence, first reported July 24, 2026 — including a cluster of independent automated firewall/blocklist reports firing within the same hour, and incidental unsolicited UDP traffic to port 3478 (STUN/TURN) suggesting a possible secondary VoIP/NAT-traversal role alongside the primary C2 function. RIPE Atlas probe data shows the entire /24 is announced by two competing origin ASNs — AS219502 (Storm Industries LLC, RPKI/IRR valid) and AS48678 (Pentech Bilisim Teknolojileri, Turkey, RPKI/IRR **invalid**) — a genuine routing irregularity rather than simple GeoIP disagreement.

Sakura was not the only payload captured this week. A separate campaign on August 27–28 delivered **RedTail**, a publicly-tracked XMRig-based cryptominer active since January 2024, tied here to CVE-2021-41773 (Apache HTTP Server path traversal/RCE).

![WTIR-12 Threat Actor 3 VirusTotal RedTail](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-12/WTIR-12%20Threat%20Actor%203%20VirusTotal%20RedTail.png)

A third, unrelated incident on September 3 dropped a second cryptominer, **Multiverze**, disguised under the filename `sshd` to blend into legitimate process listings, delivered via direct root SFTP access rather than fresh web exploitation. A fourth incident planted a malicious SSH public key directly into an `authorized_keys` file — classified **trojan.shell/malkey** — a backdoor persistence mechanism tied to the same cryptomining ecosystem.

**MITRE ATT&CK mapping:**

| Behavior | ATT&CK Technique | Note |
|---|---|---|
| Default IoT credential brute-force | T1110.001 (Brute Force: Password Guessing) | The credential-guessing activity itself |
| Exposed Telnet/SSH used as initial-access vector | T1133 (External Remote Services) | The honeypot's exposed remote-access service is the leveraged entry point; distinct from the credential-guessing technique above |
| Payload retrieval via loader script | T1105 (Ingress Tool Transfer) | Confirmed HTTP-based transfer from the staging server |
| C2 check-in with device fingerprinting | T1095 (Non-Application Layer Protocol) | Gafgyt/Mirai-family C2 (`sockprintf`/`initConnection` per VirusTotal's behavioral analysis) runs over a custom raw-socket protocol, not a standard web protocol — T1071 (Application Layer Protocol) would overstate precision here |
| DDoS flood execution | T1498 (Network Denial of Service) | Covers both direct floods (TCP/UDP) and the observed Valve Source Engine reflection/amplification flood; sub-techniques T1498.001 and T1498.002 both apply depending on flood type invoked |
| SSH key persistence (MalKey) | T1098.004 (Account Manipulation: SSH Authorized Keys) | Direct match — key written to `authorized_keys` |

**Assessment — Confidence: High.** A multi-architecture Gafgyt/Mirai DDoS botnet with externally-corroborated, hash-matched delivery infrastructure, captured alongside two independently-confirmed cryptomining families (RedTail, Multiverze) and one SSH persistence mechanism (MalKey) — three malware families and one persistence mechanism recovered and verified in a single reporting period, the first such confirmation in this series.

**Defensive relevance:** The credential list used here is publicly known and has been since Mirai's original 2016 source leak; any exposed Telnet or SSH service still accepting factory-default IoT credentials will be found by this kind of automated scanning. Separately, CVE-2021-41773 (patched in Apache 2.4.51, released October 2021) remains actively exploited nearly five years later — patch status on any internet-facing Apache instance should be confirmed directly rather than assumed.

## Lessons and Open Threads

**Volume records don't earn a pass on verification — if anything, they need more of it.** The gap between this period's raw index count (19.9M) and reported total (1.53M) was the largest seen in this series, entirely attributable to non-attack telemetry sharing the same index. Every headline number here was filtered to its specific honeypot type and spot-checked against a raw log file before being written down. This was also an extended, nine-day collection window rather than the series' usual seven — the record volume reflects that longer window and shouldn't be read as a directly comparable weekly rate against prior reports.
