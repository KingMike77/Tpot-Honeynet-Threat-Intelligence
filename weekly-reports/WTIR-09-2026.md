The honeynet logged 854,000 events this week, up about 22% from last week's 702,000. Most of that jump came from one place: Ciscoasa, which tripled in volume and moved from third place to first. Figuring out who was behind that jump became this report's main thread — and it led straight back to something from last week I didn't expect to see again so soon.

WTIR-08's flagship finding was two Ciscoasa clusters, tagged Georgia and Kazakhstan, that shared an abuse-contact domain (`zerolimit-servers.cool`) and a disputed registrant. That report ended with a note to watch for the domain resurfacing under a new IP. It resurfaced the very first week I checked. A third Ciscoasa-heavy cluster — this one spread across several conflicting country tags — ties back to the same domain and the same RIPE organization name found on last week's Kazakhstan block.

Meanwhile, UNMANAGED LTD — the Romanian actor first profiled in WTIR-07 and reprofiled in WTIR-08 as the largest single-actor volume in the series — came back for a third straight week at almost the same volume. It added a new toolkit signature (active scanning of Asterisk/FreePBX endpoints) and, once I checked its Suricata data directly, showed the same Fortinet SSL VPN exploit attempts as last week.

**Key findings**

- Ciscoasa's 299,000-event spike passed three checks — source-IP spread, concentration, and timestamp duplication — the same checks that caught two ConPot logging bugs earlier in the series.
- `zerolimit-servers.cool` and the RIPE organization name Vlad Cojuhari showed up again under a third ASN this week. This strengthens the case that WTIR-08's infrastructure family is still active, though who's actually behind it is still unconfirmed.
- UNMANAGED LTD returned for a third week at nearly the same volume, added new Asterisk/FreePBX scanning, and showed renewed Fortinet exploit attempts (CVE-2018-13379) via the same Suricata signatures that flagged it in WTIR-08.
- The China Telecom actor showed a clean, consistent SSH password-guessing pattern against a fixed `root` account, backed up by AbuseIPDB, APNIC, GreyNoise, and 15 OTX pulses.

## What I Changed This Week

**I started checking new IOCs against every past WTIR, not just last week's.** The `zerolimit-servers.cool` domain and the "Vlad Cojuhari" name only came up this week because I happened to recognize them while running a routine RIPE lookup on an unrelated-looking UK cluster. That was luck more than process. From now on, checking every new domain, name, and abuse contact against the whole series — not just the most recent report — is a standing step.

**I started treating GreyNoise's "Not Observed" result as useful information, not a blank.** GreyNoise's own guidance says that if you see an IP behaving maliciously but GreyNoise's sensors haven't picked it up, that can mean the IP is targeting something specific rather than scanning everything. I used to treat "Not Observed" as "nothing to report." It's actually a signal about scope, and I now note it explicitly.

**I started building a table any time three or more sources disagree on an actor's location.** This week's UK-tagged cluster hit six different country claims from six sources. A table made that pattern obvious in a way a paragraph didn't, so I'll use this format going forward whenever three or more sources conflict.

**I added a concentration check to Ciscoasa's spike verification.** On top of the usual unique-IP and timestamp checks, I now compare the population's average hits-per-IP against the top offender's actual hits-per-IP. A honeypot can pass both older checks and still be worth a second look if a handful of IPs are carrying way more than their share — which is exactly what happened here.

**I learned that a timestamp collision by itself doesn't mean a logging bug.** The Romania actor's Honeytrap traffic showed 11.7 records sharing every timestamp — worse than anything else this week — and my first instinct was to treat it like the old ConPot problem. Breaking it down by destination port showed the real cause: a fast, broad port sweep hitting thousands of different ports within the same one-second windows. The real question isn't just "do timestamps collide," it's "do they collide on the *same* target or across many different ones."

## Methodology

This report covers a public T-Pot honeynet's traffic over seven days, August 8 through August 15, 2026. Sources: Elastic/Kibana dashboards and T-Pot logs, cross-checked against Hurricane Electric's BGP Toolkit (including RIPE RDAP and WHOIS), plus Shodan, VirusTotal, AbuseIPDB, GreyNoise, Cisco Talos, and OTX AlienVault.

**Recurrence checks.** Every new IP, ASN, domain, and organization name gets checked against every past WTIR report before a profile is finalized. That's the step that connected this week's Investigation 1 back to WTIR-08.

**Confidence ratings.** Every finding gets its own confidence tier, since some conclusions are much better supported than others.

| Tier | What it means | Example |
|---|---|---|
| **High** | Seen directly in this honeynet's own data, with strong support from multiple other sources and nothing that contradicts the core finding | Honeypot data + a scanner's own observation + independent abuse reports, all agreeing |
| **Medium** | Seen directly in this honeynet's own data, but only lightly supported elsewhere, or with some unresolved ambiguity | Honeypot data + one supporting outside source |
| **Low** | A reasonable explanation given the evidence, but mostly inference rather than direct confirmation | A shared organization name suggests two clusters are linked, but nothing proves common control |

A rating applies to a specific finding, not a whole IP. The same actor might get High confidence for "this is a scanner" and only Low confidence for "this is the same person as last week."

**A note on terms.** An *event* is a single record T-Pot writes to Elastic. An *alert* is a Suricata detection against that traffic. A *hit* is a neutral word for one record matching a search. *Attack* or *activity* is my own read of what one or more events mean — not an exact count. One network request can produce one honeypot event and several Suricata alerts at once, which comes up in Investigation 2 this week, so these words aren't interchangeable even where I use them loosely.

**What this data can't tell you.** GeoIP and most location lookups don't reliably show where an operator physically is. Honeypot event counts are telemetry, not confirmed unique attacks. A Suricata signature match means traffic matched a known exploit pattern — it doesn't mean the exploit actually worked. Different reputation databases sometimes pull from the same underlying data, so several of them agreeing isn't the same as several independent confirmations, unless a source explicitly says it observed something first-hand. A unique timestamp is supporting evidence that an event is real, not proof. An IP or ASN's registered owner tells you who administers the network, not who's actually behind the keyboard.

Ciscoasa's jump — 109,000 to 299,000 — is almost entirely the cluster in Investigation 1. **Checking the Ciscoasa spike.** Two earlier ConPot bugs (WTIR-06 and WTIR-07) both started out looking like ordinary spikes. So a jump this size gets the same scrutiny before I trust it. Filtering to `type:"Ciscoasa"` across the week, the unique count of `src_ip.keyword` comes back at **766 distinct source IPs** behind the 299,000 hits — the spike is spread across hundreds of sources, not one.

![WTIR-09 Ciscoasa Unique Source IP Count](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-09/WTIR-09%20Ciscoasa%20Unique%20Source%20IP%20Count.png)

That still leaves a concentration question — 766 IPs averaging 390 hits each doesn't match what the top of the list actually looks like. The UK-tagged cluster's top IP, 138.226.239.5, alone accounts for 85,680 of the 299,000, way above the population average, and a very different shape than WTIR-08's Georgia and Kazakhstan clusters, where the top five IPs were all within a few hundred hits of each other. Concentration by itself isn't a red flag — a dedicated scanner hammering one honeypot type harder than everyone else is normal — but it's exactly the shape that deserves the timestamp check that caught ConPot's bugs.

Filtering to that one IP, the unique count of `@timestamp` comes back at **85,504** against 85,680 total records — 99.8% unique, with only 176 records sharing a timestamp with anything else. ConPot's bug produced the opposite pattern: a big gap between total records and unique timestamps from the same source logging the same event over and over. Nothing like that shows up here. This check is supporting evidence, not proof — a bug could in theory write duplicates under different timestamps, and two real events could coincidentally share one — but it specifically rules out the exact failure mode ConPot had, which is what it's designed to catch.

Some collision is expected from an automated brute-forcer firing password attempts quickly, and this is well short of what a duplicate-write bug would produce. Cowrie's numbers are clean.

| 138.226.239.4 | 81,694 |

![WTIR-09 United Kingdom Threat Actor](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-09/WTIR-09%20United%20Kingdom%20Threat%20Actor.png)

Secondary honeypots in this traffic: Honeytrap, Cowrie, Sentrypeer, Mailoney, and Dionaea, all far lower volume. Top ports: 5060 (SIP), 22 (SSH), 10443, 25 (SMTP), and 3341.

I pulled OSINT the way I do for every actor in this series, and this is where it got interesting. Cisco Talos was the source that stopped me — it returned Port Vila, Vanuatu, a country I'd never run into in this series and, honestly, couldn't have placed on a map before this week. Vanuatu is a small Pacific island nation east of Australia — a chain of islands with a capital and a population of roughly 323,000 — nowhere near the United Kingdom the honeynet's own GeoIP had already tagged this cluster with.

![WTIR-09 Vanuatu Location Map](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-09/ChatGPT%20Image%20Aug%2015%2C%202026%2C%2008_15_48%20PM.png)

That gap between the dashboard and a single outside lookup is exactly the kind of thing this series has trained me to stop and check, rather than skim past — the same instinct that turned Georgia and Kazakhstan into WTIR-08's flagship investigation. So I kept pulling sources instead of settling on one. Here's what came back:

| Source | Country/location claimed |
|---|---|
| T-Pot Elastic GeoIP | United Kingdom |
| Cisco Talos WHOIS | Port Vila, Vanuatu |
| AbuseIPDB / IPinfo | Amsterdam, Netherlands |
| RIPE RDAP org record | Vanuatu (org field), with contact phones from Moldova and Seychelles |
| OTX AlienVault | Switzerland |
| GreyNoise / ipinfo | Netherlands |
| VirusTotal | United Kingdom |

A few of these sources may draw on overlapping commercial location data rather than each being a fully separate measurement — AbuseIPDB, GreyNoise, and IPinfo can share underlying datasets, and VirusTotal is really an aggregate of many vendors, not one voice. Even accounting for that, the disagreement stands out, because RIPE's own registration record — not a location product, just what the registrant actually typed in — is internally inconsistent on its own.

This is more disagreement than any other actor in this series, and it meaningfully lowers confidence in any single location claim here. The RIPE record made things more specific, not more resolved. The registrant org is listed as **Vlad Cojuhari**, at "Constantin Brancusi St 3," with an admin contact phone using a Moldova country code and a technical contact phone using a Seychelles country code — neither matching the org's own claimed Vanuatu country field. The abuse contact routes through **`zerolimit-servers.cool`**, and the WHOIS remarks read more like an informal VPS reseller's boilerplate than a real broadband ISP's abuse desk. The netblock was created November 22, 2025; the AS213474 route object was created May 6, 2026. Both check out as valid registration data. The recent dates are worth noting, but age alone doesn't prove malicious infrastructure. All of this fits infrastructure whose ownership or location is obscured, inconsistent, or frequently reassigned — it doesn't by itself prove deliberate anonymization, since stale records, resold VPS blocks, and reseller arrangements can all look the same from outside.

That registrant name and domain aren't new to this series. WTIR-08's flagship investigation, "Two Passports, One Infrastructure Cluster," documented a Ciscoasa cluster on 185.136.15.0/24 (AS205997, tagged Kazakhstan) with the RIPE netname **Vlad Cojuhari**, linked by a shared `zerolimit-servers.cool` abuse contact to a second cluster on 77.91.71.0/24 (AS211486, tagged Georgia). That report ended with a note to watch for the domain resurfacing. It did — under a third ASN, a new set of conflicting country claims, and the same RIPE organization name, in the very next report.

AbuseIPDB independently confirms this cluster is active and malicious. 138.226.239.5 carries a 100% abuse-confidence score, 162 reports from 71 distinct sources, first reported July 7, 2026, with the most recent report two days before this collection window closed. The captured traffic goes well beyond Cisco. Reporters logged `GET /sslvpn_logon.shtml` and `GET /api/sonicos/is-sslvpn-enabled` (both SonicWall SonicOS SSL-VPN endpoints), plus `/remote/login` (also used by Fortinet FortiGate SSL-VPN portals), along with scanning on non-standard high ports (58443, 15443, 7443, and port 9). One reporter's ID, `bsts-tpot-hive`, shows another separate T-Pot HIVE deployment also caught this IP — independent honeypot telemetry outside this installation, which supports reading this as broad automated scanning rather than something aimed at this network specifically. This honeynet's own Ciscoasa numbers most likely reflect that emulator catching a generic ASA-adjacent probe, not the actor's only target — it looks like it's fingerprinting whichever SSL-VPN vendor happens to respond.

GreyNoise adds a useful but not conclusive signal. It came back **Not Observed** for 138.226.239.5 — meaning GreyNoise's own sensors hadn't seen this IP scanning within the relevant window. GreyNoise's guidance is that traffic seen by an organization but not by GreyNoise's own network can be consistent with more targeted activity, especially against a specific software stack — which lines up with the VPN- and honeypot-adjacent targeting seen in the AbuseIPDB data. This doesn't prove the actor is specifically targeting this honeynet. Limited sensor coverage, IP churn, or freshly stood-up infrastructure could produce the same result. GreyNoise's metadata also surfaced a second, conflicting domain, `homelinebb.com`, distinct from `zerolimit-servers.cool` — more evidence of a loosely managed or recently repurposed netblock.

OTX AlienVault adds the Switzerland claim above and nothing else useful for this specific IP.

VirusTotal adds a seventh data point — and it's the first one to actually agree with something. For 138.226.239.4, VirusTotal's own country field reads **GB**, matching the original GeoIP tag rather than any of the other five sources. 7 of 91 security vendors flag it, community score -1: BitDefender and G-Data tag it Phishing; Cluster25, CRDF, and SOCRadar tag it Malicious; Fortinet and MalwareURL tag it Malware; three more (alphaMountain.ai, AlphaSOC, Gridinsoft) rate it Suspicious. As with the Phishing tags on WTIR-08's Alsycon/HostUS actor, these Phishing labels most likely reflect the wider block's reputation rather than phishing this honeynet actually observed — everything captured here is SonicWall, Fortinet-style, and Cisco ASA-adjacent scanning.

Seven sources now disagree on where this cluster sits: GeoIP and VirusTotal both say United Kingdom; Talos says Vanuatu; AbuseIPDB and GreyNoise both say Netherlands; RIPE's org field says Vanuatu with Moldova and Seychelles contacts; OTX says Switzerland. That's a plurality for the UK, not confirmation — especially given how inconsistent the RIPE record is on its own.

**Assessment. Confidence: High** that this cluster was actively scanning multiple SSL-VPN vendors (SonicWall, Fortinet-style) during the collection window — backed by AbuseIPDB report volume, the captured payloads naming specific endpoints, and observations from another honeypot deployment. **Confidence: High** that this cluster shares an infrastructure or registration relationship with WTIR-08's Georgia and Kazakhstan clusters, based on the matching RIPE organization name and abuse-contact domain. **Confidence: Low-to-Medium** that all three clusters are run by the same person or group — a shared organization name and abuse domain show an infrastructure or administrative link, not necessarily one human operator, since the same registration record can sit behind a reseller, shared hosting, or a shared toolkit vendor used by more than one actor. **Confidence: Low** on the operator's actual physical location — seven separate sources produced only a plurality for the UK against five other answers spanning Vanuatu, the Netherlands, and Switzerland, some of which may share underlying data rather than independently confirming anything, and RIPE's own contact details contradict each other.

## Investigation 2: The Toolkit for Hire, Round Three (Romania)

**193.46.255.112 (UNMANAGED LTD, AS47890) — now in its third straight week in this series.**

First profiled in WTIR-07, reprofiled in WTIR-08 at 165,061 hits (the largest single-actor volume the series had seen), where its own Suricata data confirmed active exploit attempts against CVE-2018-13379, the FortiOS SSL VPN path traversal bug. It's back this week at nearly the same volume — 163,513 hits — again mostly through Honeytrap.

![WTIR-09 Romanian Threat Actor Elastic Dashboard](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-09/WTIR-09%20Romanian%20Threat%20Actor%20Elastic%20Dashboard.png)

This week's breakdown: Honeytrap at roughly 161,000, with Cowrie, Mailoney, ConPot, Miniprint, Redishoneypot, Dionaea, Tanner, H0neytr4p, and Adbhoney far behind. Ports: 25 (SMTP), 9100 (printer/JetDirect), 50100, 6379 (Redis), and 10001. The Suricata alert category histogram shows steady Misc Activity and Generic Protocol Command Decode through most of the week, with a sharp spike on August 15th.

![WTIR-09 Romanian Threat Actor Histogram and Password Tagcloud](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-09/WTIR-09%20Romanian%20Threat%20Actor%20Histogram%20and%20Password%20Tagcloud.png)

The new detail this week showed up in the raw request logs. The honeypot captured the literal headers of an unauthenticated scripted client: `Connection: keep-alive` and `User-Agent: python-requests/2.6.0 CPython/2.7.5 Linux/3.10.0-1160.119.1.el7.x86_64` — a Python 2.7.5 interpreter typical of a default CentOS/RHEL 7 install. The request paths show repeated `GET`s for `/admin/i18n/readme.txt`, `/admin/config.php` (including a double-slash variant), `/_asterisk/phpversions.php`, `/_asterisk/graph.php`, `/restapps/`, `/r0r.php`, `/assets/phpversions.php`, and `/phpversions.php`.

![WTIR-09 Romanian Username Tagcloud](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-09/WTIR-09%20Romanian%20Username%20Tagcloud.png)

The `/_asterisk/` paths, together with `phpversions.php` and `graph.php`, are consistent with automated scanning of Asterisk/FreePBX web-management pages — historically a target for information leaks and code-execution chains. That's a new toolkit signature for this actor. WTIR-08 documented Fortinet SSL VPN exploit attempts (CVE-2018-13379) confirmed by Suricata; this week the same actor is also actively probing VoIP/PBX systems and generic admin panels, on top of its established Fortinet targeting. That fits the "whatever is listening" opportunistic pattern WTIR-08 assigned it, now with a concrete example beyond just the port list.

A direct Suricata check this week filled that gap. Filtering `src_ip.keyword:"193.46.255.112" and alert.cve_id.keyword:*` and grouping by CVE ID shows CVE-2018-13379 as the dominant tag, plus three low-volume ones worth flagging separately: CVE-2002-0013 (6 hits), CVE-2019-11500 (4 hits), and CVE-2016-5696 (1 hit). The CVE panel itself has a display quirk — CVE-2018-13379 shows up as two differently-formatted multi-value entries instead of one clean row. That's just a formatting artifact of a multi-value field, not two separate findings, and the signature-level breakdown below clears it up.

Breaking the same traffic down by `alert.signature.keyword` confirms the same two exploit-classified signatures that justified T1190 in WTIR-08 fired again this week: `ET EXPLOIT FortiOS SSL VPN - Information Disclosure (CVE-2018-13379)` at 2,110 hits, and `ET EXPLOIT Fortinet FortiOS/FortiProxy SSL VPN Web Portal Path Traversal (CVE-2018-13379)` at another 2,110 hits. A third signature, `GPL WEB_SERVER apache directory disclosure attempt`, also hit exactly 2,110 times — the same count as each Fortinet signature. That strongly suggests all three are firing on the same underlying set of requests, not three separate waves, so these counts shouldn't be added together. The most defensible read is roughly **2,110 underlying requests** matching the CVE-2018-13379 exploit signatures, not 6,330 separate events. An earlier draft of this section incorrectly summed the two Fortinet signatures to 4,220 — I'm correcting that here. The top of the signature list by raw volume is mostly non-exploit noise: `ET INFO User-Agent (python-requests) Inbound to Webserver` at 87,423 hits, confirming the scripted-client fingerprint above at a much bigger scale than the individual request captures suggested, followed by stream and ICMP noise from the broader scan.

The three low-volume CVE tags (CVE-2002-0013, CVE-2019-11500, CVE-2016-5696) are noted, not confirmed. Single-digit hits with no matching exploit signature checked is a much weaker bar than the Fortinet finding cleared, and it's worth a direct signature-level check next report rather than an assumption.

**Assessment. Confidence: High** that this is the same recurring infrastructure source seen in WTIR-07 and WTIR-08, based on the identical IP, ASN, recurring volume, and consistent target profile across three straight weeks — though this alone doesn't prove the same human operator or organization is behind it. **Confidence: High** that traffic matching CVE-2018-13379 Fortinet SSL-VPN exploit signatures showed up again this week, based on the same two exploit-classified Suricata signatures that established the WTIR-08 finding; this shows exploitation-pattern traffic, not confirmed successful exploitation, since the telemetry shows matching traffic, not proof a vulnerable target actually returned data. **Confidence: Medium** that the new Asterisk/FreePBX scanning is an intentional toolkit addition rather than background noise — it's backed by concrete path and user-agent evidence, but not by an exploit-classified Suricata signature the way the CVE-2018-13379 finding was. **Confidence: Low** on the three low-volume CVE tags — single-digit hits with no confirmed exploit signature aren't enough to call these real exploit attempts versus background noise.

## Investigation 3: Same Country, Different Story (China)

**58.34.44.122 (CHINANET Shanghai / China Telecom, AS4812) — a new actor this week, and a good contrast to Investigation 1.**

WTIR-08 profiled a different China-tagged actor, 222.128.21.18 under China Unicom Beijing (AS4808), likely a compromised residential or business host, based on a shorter abuse history and a lower GreyNoise severity rating. This week's actor is a different IP, a different ASN, and — once the OSINT came back — a much cleaner confidence picture.

![WTIR-09 China Threat Actor Elastic Dashboard](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-09/WTIR-09%20China%20Threat%20Actor%20Elastic%20Dashboard.png)

58.34.44.122 generated 20,171 hits, almost all against Cowrie, targeting ports 22 and 2222. Every SSH login attempt used the `root` username, while the password guesses varied. That's password guessing against a known account, not username enumeration. The password list is where the variation lives, and it's distinctive — instead of common weak passwords, a lot of entries look like numeric, date-derived strings: `020289`, `02020202`, `01121989`, `020288`, `01041990`, `01071987`, `01091992`, `01021987`, `010985`, `01021983`, `007007007`, `001974`, `010102`, `010289`, `012012`, `0202021`, `010488`, `01011991`, `010191`, `01011979`, `01031988`, `01234567890`. Many resemble dates or years, but the list doesn't stick to one consistent date format — `020289` could just as easily be DDMMYY or MMDDYY, and a few, like `007007007`, don't look like a date at all, more like generic dictionary entries.

![WTIR-09 China Threat Actor Password Tagcloud](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-09/WTIR-09%20China%20Threat%20Actor%20Password%20Tagcloud.png)

Unlike Investigation 1, every source checked here points the same direction — though it's worth being precise about what each one actually shows rather than treating them as interchangeable. APNIC RDAP confirms the network's allocation and ownership, not malicious behavior. AbuseIPDB and OTX confirm community-observed malicious activity. GreyNoise confirms first-hand scanning behavior and classification. VirusTotal is an aggregate of vendor opinions, not its own independent observation. Together they converge strongly on this IP's identity, ownership, and malicious SSH activity, even though they're not all measuring the exact same thing.

AbuseIPDB: 100% abuse confidence, 503 reports from 141 distinct sources, first reported May 15, 2025, most recent report 14 hours before this write-up — including a log excerpt from an independent reporter showing `Failed password for root from 58.34.44...`, the exact same root-targeted pattern seen here. APNIC RDAP: a clean, long-established CHINANET-SH allocation registered in 2008, with consistent, unchanged contact details — the opposite of Investigation 1's shell-registration red flags. A DNSBL check shows it failing 2 of 83 blocklist tests (`rbl.interserver.net` and `zen.spamhaus.org`). GreyNoise: malicious, not spoofable, first-hand observed, tagged SSH Bruteforcer, SSH Connection Attempt, SSH Alternative Port Crawler, and Web Crawler — the Alternative Port Crawler tag directly matches the dual-port 22/2222 targeting seen here. OTX AlienVault: 15 separate community pulses, almost all tagged Bruteforce, Brute-Force, SSH, Honeypot, or Scanner, from operators in Malaysia, Australia, and elsewhere over more than a year.

VirusTotal adds one more data point, at a higher detection rate than Investigation 1's IOC: 11 of 91 vendors flag 58.34.44.122 malicious, community score -3. ADMINUSLabs, Chong Lua Dao, CINS Army, Cluster25, Criminal IP, GreyNoise, and Lionic tag it Malicious directly; Fortinet tags it Malware; BitDefender, G-Data, and VIPRE tag it Phishing; five more (alphaMountain.ai, AlphaSOC, CyRadar, Gridinsoft, SOCRadar) rate it Suspicious. As with Investigation 1's Phishing tags, these most likely reflect the wider CHINANET-SH block's history rather than phishing this honeynet actually saw — everything captured here is SSH password guessing.

**Assessment. Confidence: High** that this IP is running sustained SSH password guessing against a fixed `root` account — backed by this honeynet's own data matching GreyNoise's first-hand observation of the same crawling behavior, plus substantial AbuseIPDB and OTX support. **Confidence: Medium** that the source is a compromised or repurposed host rather than dedicated attacker-owned infrastructure — the long-standing, legitimate CHINANET-SH allocation makes that plausible, but nothing here distinguishes a compromised machine from a rented or intentionally operated one on the same allocation. **Confidence: Low** on the date-pattern password interpretation — the values resemble date-like numbers, but no outside source confirms that reading, and the list could just be a botnet's built-in numeric dictionary.

## What This Week Taught Me

The `zerolimit-servers.cool` recurrence is the clearest lesson of the week. WTIR-08 ended with a note to watch for that domain resurfacing under a new IP, and it did — under a third ASN and a new set of conflicting country tags, within seven days. That's the kind of pattern that only shows up if you actually go back and check, instead of treating every week's cluster as a fresh, unrelated case. The RIPE organization name, Vlad Cojuhari, matched too, which made this a much stronger connection than a shared domain alone would have been.

The contrast between Investigation 1 and Investigation 3 is the same lesson WTIR-08 drew from its own China actor, sharpened. A netblock with recent creation dates and inconsistent registration and location data is a fundamentally different problem than a compromised host on an 18-year-old, well-documented ISP allocation — even when both are actively malicious and both clear High confidence on the core behavioral finding. Confidence tiers measure how well-supported a claim is, not how dangerous the actor is, and this week made that distinction concrete again.

GreyNoise's "Not Observed" status turned out to be more useful than I expected. Instead of treating it as a lack of information, I found it adds real context alongside the honeynet's own observations — in this case, nuance on whether the scanning was broad internet noise or something more selectively targeted. It still can't prove targeting on its own, but it's worth recording as part of the picture.

The UNMANAGED LTD Suricata check is a smaller lesson, but worth saying plainly: I initially wrote this report saying I couldn't confirm whether last week's Fortinet exploit attempts continued, instead of actually going and checking. Once I checked, the same two exploit-classified signatures fired again. An unconfirmed gap in a draft isn't the same as a genuinely unanswerable question — it's worth closing gaps like that before publishing instead of leaving them as caveats.

A few things worth checking next week: whether `zerolimit-servers.cool` or `homelinebb.com` shows up under a fourth ASN, whether UNMANAGED LTD's Asterisk scanning shows up again or was a one-off, whether the China Telecom password pattern reappears under other source IPs, and whether Georgia showing up in this week's top 10 countries is coincidence or the start of another thread.

## What Remains Unconfirmed

- The physical location of the operator behind AS213474 and 138.226.239.0/24. Seven separate sources produced only a plurality for the UK, and RIPE's own contact details contradict each other.
- Whether the three `zerolimit-servers.cool` clusters (AS211486, AS205997, AS213474) are controlled by the same person or group, or share the registration record for some other reason — a reseller arrangement or a shared toolkit vendor, for example.
- Whether UNMANAGED LTD's Asterisk/FreePBX scanning this week is a persistent toolkit addition or a one-time thing. No exploit-classified Suricata signature backs it the way CVE-2018-13379 is now backed for a second week.
- Whether UNMANAGED LTD's low-volume CVE tags (CVE-2002-0013, CVE-2019-11500, CVE-2016-5696) reflect real, low-intensity exploit attempts or just background noise. Single-digit hits with no confirmed signature aren't enough to call it either way yet.
- Whether the host at 58.34.44.122 is a compromised residential or business machine, or a rented, managed, or otherwise intentionally operated host on the same legitimate CHINANET-SH allocation.
- Whether the China Telecom date-pattern password list is specific to this host or a shared default dictionary used more broadly by the same botnet — no outside source confirms the pattern.
