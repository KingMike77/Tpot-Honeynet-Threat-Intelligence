## A Note Before We Begin

If you follow this project, you may have noticed that WTIR-02 never came out on schedule. The honest reason is that I got the flu. By the time I was back on my feet, three weeks of attack data had accumulated and I had a different problem to deal with — the honeynet itself.

When I first set up this T-Pot deployment, I did not think carefully enough about what happens to storage and memory over time. T-Pot feeds every attack event into an Elasticsearch database, and that database grows constantly. After several weeks of 24/7 attack collection, the Elasticsearch and Logstash stack started running out of Java heap memory on the 8GB Proxmox VM that hosts this deployment. Logstash kept crashing mid-pipeline, which is why the live attack map stopped updating and new data stopped appearing in Kibana.

I spent time trying to tune the memory settings, reduce heap allocations, and clear the backlog, but the root cause was that I had not planned for long-term data growth from the beginning. That is on me. I have since put a 7-day automatic data retention policy in place so old indices are cleaned up automatically, and I reset the entire T-Pot environment after collecting all the data needed for this report. The honeynet is now running clean.

I also ran into a resource issue during the OSINT research phase. The SpiderFoot scans I was running to profile threat actors consumed so much CPU and memory alongside the honeypot containers that the VM became completely unresponsive and I had to hard reset it from the Proxmox console. The SpiderFoot scans for Actor 2 and Actor 3 were aborted as a result. I supplemented the missing data with manual lookups in AbuseIPDB, Shodan, Talos Intelligence, and GreyNoise. Actor 1 received a complete SpiderFoot scan with 20,150 findings before the crash occurred. Going forward, I will run SpiderFoot on a separate machine so it does not compete with the honeypot stack for resources.

These are real problems that come with running a lab on consumer hardware. Documenting them honestly is part of what this project is about.

## What Attackers Were Trying to Log In With

The credential data captured by Cowrie and Heralding this period tells an interesting story on its own.

The most common username attempts were `root` and `admin` by a wide margin, which has been consistent across every reporting period. But a few things stood out this time. The usernames `solana`, `firedancer`, and `raydium` appeared repeatedly. These are all names from the Solana blockchain ecosystem. Solana is a proof-of-stake blockchain, Firedancer is a high-performance validator client built by Jump Crypto, and Raydium is a decentralized exchange built on Solana. The password `solv123` appeared alongside these usernames. This is not a coincidence — someone built a credential dictionary specifically targeting Solana validator nodes and cryptocurrency infrastructure. The usernames `openclaw` and `owncloud` also stood out, suggesting some attackers were going after specific self-hosted applications.

On the password side, the most common attempt was a blank password — meaning no password at all. This reflects how many internet-exposed services are deployed with no authentication configured. After blank passwords, the list was dominated by `password`, `123456`, `1234567890`, and keyboard walk patterns like `1qaz@WSX`, `1q2w3e4r`, and `1qaz2wsx`. These patterns show up in automated credential dictionaries targeting users who think typing across the keyboard in a diagonal line makes for a strong password.

### Actor 1 — 108.181.63.2 | A Windows Machine Hammering VoIP Infrastructure

**109,689 hits | Rank #2**

![Kibana dashboard filtered to 108.181.63.2 showing 110k hits exclusively on Sentrypeer from Psychz Networks AS40676](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-02/actor1-kibana.png)

Every single one of the 109,689 hits from this IP went to the Sentrypeer honeypot. Sentrypeer emulates a SIP phone system, so this IP was not doing broad scanning — it was specifically going after VoIP infrastructure.

The first thing we looked at was where this IP came from. It belongs to AS40676, which is Psychz Networks, a US-based hosting provider based in Walnut, California. Psychz Networks is well known in the threat intelligence community for hosting malicious infrastructure and responding slowly to abuse reports. The IP sits in a /23 netblock — 108.181.62.0/23 — that was reallocated from TELUS Communications to Psychz Networks in July 2023. When we ran the SpiderFoot scan, every single IP in the adjacent /24 subnet (108.181.63.0 through 108.181.63.15) came back flagged as malicious by multiple sources. This is not one bad IP. This is a block of coordinated malicious infrastructure.

Shodan gave us a clearer picture of what this machine actually is. The hostname is `WIN-86U1TEOEMLL` — that default-looking name is a strong indicator of a freshly provisioned or deliberately unconfigured Windows Server. Shodan found port 3389 open (Remote Desktop Protocol), port 135 (Microsoft RPC), and a full stack of Windows RPC services on ports 10496 through 10503. The exposed services included MS-SAMR (Security Account Manager), MS-TSCH (Task Scheduler), MS-RPRN (Print Spooler), and MS-SCMR (Service Control Manager). That is a very large attack surface for a machine that is supposed to be sending traffic, not receiving it.

![P0f OS fingerprinting confirming 100% Windows NT kernel for all traffic from 108.181.63.2](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-02/actor1-p0f.png)

P0f, the passive OS fingerprinting tool built into T-Pot, confirmed that 100% of the traffic from this IP came from a Windows NT kernel. That lines up exactly with what Shodan found.

The attack tool being used was SipVicious, a well-known VoIP attack toolkit used for SIP scanning, extension enumeration, and credential brute forcing. Suricata fired the signature `ET VOIP Modified Sipvicious Asterisk PBX User-Agent` during the session. Beyond the credential attacks, Suricata also detected 17 attempts matching `ET EXPLOIT Possible CVE-2014-6271 Attempt Against SIP Proxy`. CVE-2014-6271 is Shellshock — a vulnerability in the Bash shell that allows remote code execution via crafted environment variables. It was disclosed in 2014 and it is still being actively thrown at things that have not been patched. The fact that this actor was attempting Shellshock against our SIP honeypot means they were not just trying to guess passwords — they were trying to execute code on the server itself.

AbuseIPDB had 540 reports from 134 distinct sources at the time of writing, with a 100% abuse confidence score. The IP was first reported on May 27, 2026, and the most recent report came in 53 minutes before this report was published. It was still actively attacking. GreyNoise observed this IP hitting targets in more than 90 countries across SIP scanning, web crawling, and HTTP OPTIONS probing.

**What the data tells us:** This is a Windows Server on Psychz Networks bulletproof hosting that is being used as a dedicated VoIP attack platform. The full exposure of Windows RPC services and RDP suggests whoever is operating this machine has remote access to it and is running SipVicious and Shellshock exploit code from it. The subnet-wide malicious classification suggests this is not an isolated compromised machine but part of a coordinated infrastructure block.

### Actor 2 — 5.83.143.40 | VNC Brute Force with Nation-State Malware Signatures

**83,323 hits | Rank #3**

![Kibana dashboard filtered to 5.83.143.40 showing 83k hits exclusively on Heralding from Joel Krause AS200912 Netherlands](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-02/actor2-kibana.png)

Every hit from this IP went to the Heralding honeypot on port 5900. Port 5900 is VNC — Virtual Network Computing, a remote desktop protocol widely used for server management and remote access. This actor was not doing anything broad. It was looking specifically for VNC servers.

The IP is hosted by VpsLayer Hosting, operated by Joel Krause under AS200912. The upstream provider is GHOSTnet GmbH (AS12586). Shodan showed only port 22 open — a clean Ubuntu Linux installation running OpenSSH 8.9p1. A machine with only SSH exposed and a single focused attack target is consistent with a purpose-built attack platform. The Talos hostname was `40.143.83.5.hosted-by.vpslayer.net` confirming VpsLayer hosting. Talos did not list this IP on its blocklist, which is notable — it suggests this actor avoids spam and email-based detection methods while focusing on network-level attacks that may take longer to surface in reputation systems.

![Port 5900 VNC targeting from Netherlands and password tagcloud showing keyboard walks and numeric sequences](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-02/actor2-credentials.png)

The credential data showed an empty username field across all attempts. VNC implementations often do not require a username — just a password — and this actor's dictionary reflected that. The passwords being tried were standard brute force material: `12345678`, `Password`, `abc12345`, keyboard walks like `1qaz2wsx` and `1q2w3e4r`, and repetition patterns like `00000000` and `11111111`. AbuseIPDB confirmed 18,996 VNC brute force attempts in a single 24-hour period from one reporter alone. The most recent report came in 17 minutes before this report was published.

The most significant finding for this actor came from Suricata, not from credential analysis. Two malware signatures fired during the session.

The first was `ET MALWARE J-magic (nfsiod) Backdoor Magic Packet Inbound Request M5`, with 17 detections. J-magic is a backdoor that targets Juniper Networks routers. It works by passively monitoring all network traffic for a specific magic packet — a specially crafted trigger that activates the backdoor without opening any listening port. Lumen Technologies' Black Lotus Labs publicly disclosed J-magic and attributed it to espionage-motivated threat actors targeting network infrastructure. The presence of this signature in traffic associated with this IP means the Suricata ruleset detected inbound traffic matching the J-magic magic packet pattern.

The second was `ET MALWARE Suspected BPFDoor TCP Magic Packet`, which also fired. BPFDoor is a Linux backdoor attributed to the Chinese state-sponsored threat actor Red Menshen, also tracked as Earth Bluecrow by Trend Micro. BPFDoor works by hooking into the Linux kernel's Berkeley Packet Filter system to intercept magic packets at the lowest level of the network stack. It requires no open listening ports and leaves almost no trace that standard security tools can detect. It has been found on compromised systems across telecommunications, government, and critical infrastructure targets in Asia, the Middle East, and Europe.

It is important to be precise about what this data tells us and what it does not. Suricata fired these signatures because it detected inbound traffic matching known malware patterns associated with these tools. This tells us with confidence that traffic matching these patterns was observed hitting our honeypot from this IP. What the data does not tell us definitively is whether this actor is the same group that developed these tools, or whether these tools have been adopted more broadly. The hypothesis that this actor may be using these implants to maintain persistence on successfully compromised VNC systems is consistent with the data, but that remains a hypothesis.

AbuseIPDB had 1,813 reports from 149 distinct sources, 100% confidence. GreyNoise classified this IP as malicious with tags `RFB Protocol` and `VNC Login Attempt` and confirmed the activity was observed directly by their sensor network on June 20 and 21.

**What the data tells us:** This is a Linux-based attack platform on VpsLayer/GHOSTnet hosting conducting large-scale VNC brute forcing. Suricata detected inbound traffic from this IP matching signatures for two sophisticated malware implants associated with espionage-level threat actors. Whether this represents direct use of those tools by an advanced actor, secondary distribution of those tools, or some other explanation is not something the current data can confirm with certainty.

### Actor 3 — 45.95.147.229 | A Four-Year-Old Scanner Still Targeting Fortinet VPNs

**64,410 hits | Rank #5**

![Kibana dashboard filtered to 45.95.147.229 showing 64k hits across 14 honeypot services from Alsycon B.V. AS49870 Netherlands](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-02/actor3-kibana.png)

This actor stood out from the other two immediately because of how broadly it scanned. While Actor 1 hit only Sentrypeer and Actor 2 hit only Heralding, this IP spread 64,410 hits across 14 different honeypot services. That kind of breadth is the signature of a general-purpose vulnerability scanner rather than a tool built for one specific attack type.

The IP is hosted by Alsycon B.V. (AS49870), a Dutch VPS and colocation provider based in Lelystad. The hostname registered to this IP is `prime-env1.contaprotegida.co`. In Portuguese, "conta protegida" means "protected account." The "env1" in the hostname suggests this is the first in a numbered series of environments — structured infrastructure rather than a one-off setup.

Shodan found Apache HTTP Server 2.4.6 running on port 80 and OpenSSH 7.4 on port 22. Apache 2.4.6 was released in 2013. Running a 13-year-old version of Apache with no patches carries over 50 documented CVEs including multiple remote code execution vulnerabilities with CVSS scores of 9.8. Whether this is a deliberately disposable server or a long-neglected machine is not clear from the data alone, but either way it is significantly exposed.

Talos Intelligence has had this IP on its active malicious blocklist since May 25, 2023 — more than three years before this report. AbuseIPDB shows the first abuse report was filed on September 28, 2022, making this one of the longest-running confirmed malicious IPs we have observed across all WTIR reporting periods.

When we looked at the broader subnet in Talos data, 68 or more IPs in the same 45.95.147.0/24 block were actively sending email with domain names in Portuguese and Spanish. Domains like `contaprotegida.co`, `contavalidaseg.com`, `getvalidservice.com`, and `factupagobmmx.top` appeared repeatedly. The last one translates roughly as "generating invoice payment Mexico" in Spanish. This points to phishing operations targeting Latin American businesses running alongside the scanning activity from the same infrastructure block.

GreyNoise did not observe this IP conducting mass internet scanning in the past 48 hours. That is meaningful context — GreyNoise is built to detect broad indiscriminate scanning, and when an IP does not show up there it suggests more selective or targeted behavior rather than spraying packets at everything on the internet.

![Port targeting breakdown showing ports 9100, 6379, 10001, 50100, and 25 from Netherlands infrastructure](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-02/actor3-ports.png)

The ports targeted were 9100 (network printer JetDirect), 6379 (Redis database), 10001 (commonly associated with IoT and industrial devices), 50100, and 25 (SMTP email). That combination points to an actor looking for printers, databases, and email servers alongside the web application targets.

![Web request paths showing Fortinet VPN login targeting, VtigerCRM exploitation, Asterisk PBX paths, and PHP reconnaissance](https://raw.githubusercontent.com/KingMike77/Tpot-Honeynet-Threat-Intelligence/main/Screenshots/week-02/actor3-webrecon.png)

The web paths being requested tell a clearer story. The path `//remote/login?lang=en` is the Fortinet SSL VPN login page. The path `/_asterisk/graph.php` targets Asterisk PBX phone systems. The path `/vtigercrm/graph.php` targets VtigerCRM, a business CRM platform. The paths `/admin/views/config.php`, `/admin/config.php`, and `/phpversions.php` are standard PHP reconnaissance probes looking for configuration files and version disclosure. All of these requests came from a `python-requests/2.27.1` User-Agent, which Suricata detected 63,080 times — an automated Python scanning framework sending the same requests repeatedly.

The headline finding from Suricata was 1,747 detections for CVE-2018-13379. This is a path traversal vulnerability in Fortinet FortiOS SSL VPN that allows an unauthenticated attacker to read arbitrary files from the server — including the file that stores active VPN session tokens. An attacker with those tokens can authenticate to the VPN as a legitimate user without needing a password. This vulnerability was disclosed in 2018, patched by Fortinet the same year, and has been actively exploited in the wild by multiple threat actors including groups associated with nation-state activity ever since. The fact that it is still being targeted at scale in 2026 tells us that a meaningful number of Fortinet deployments remain unpatched after nearly eight years.

Suricata also fired 299 alerts for `ET SCAN NMAP -sS window 1024`, confirming active Nmap SYN scanning alongside the web application probing.

**What the data tells us:** This is a long-running attack platform that has been confirmed malicious since at least September 2022 and is still actively scanning. It targets enterprise VPN infrastructure via a well-documented CVE, probes web applications with an automated Python framework, and operates from a subnet that also hosts what appears to be Latin American phishing infrastructure. The selective scanning behavior observed by GreyNoise suggests this actor is not blindly spraying traffic but choosing specific targets.

## What This Week's Data Suggests

VoIP systems are being actively targeted by exploit-capable attackers, not just credential stuffers. Actor 1 attempted Shellshock against our SIP honeypot, which means whoever is operating that infrastructure is trying to execute code on VoIP servers rather than just guessing extension credentials. Organizations running exposed SIP infrastructure on unpatched systems are facing a more capable threat than traditional toll fraud campaigns.

CVE-2018-13379 is still being exploited at scale in 2026. Fortinet patched this vulnerability in 2018 and has published multiple advisories about it since then. Actor 3 sent 1,747 attempts targeting it during this reporting period alone. If your organization runs FortiOS SSL VPN and has not verified it is patched against this vulnerability, that should be a priority.

VNC is a high-value target. Actor 2 sent over 83,000 brute force attempts at port 5900 and the associated Suricata signatures for J-magic and BPFDoor suggest the goal may go beyond simple access. Any VNC service exposed to the internet without strong authentication and IP allowlisting is at meaningful risk.

The Netherlands has become a notable hosting location for malicious infrastructure in this dataset. Two of three actors this week operated from Dutch ASNs, and the Netherlands ranked second in overall attack origin. This is consistent with broader reporting on the Netherlands as a hub for abuse-tolerant hosting infrastructure.

Cryptocurrency validator infrastructure is being specifically targeted. The presence of Solana ecosystem usernames in the credential telemetry — solana, firedancer, raydium — alongside the corresponding password solv123 indicates someone built a credential list specifically for this environment. If you operate blockchain validator nodes, audit your authentication configuration.

## A Note on the Infrastructure Reset

After all data for this report was collected, the T-Pot environment was fully reset. All Elasticsearch indices, Docker volumes, and accumulated attack data were wiped and the system was restarted from scratch. The reset resolved the memory management issues described at the beginning of this report. A 7-day ILM retention policy is now in place so indices older than one week are automatically deleted, keeping the Elasticsearch stack lean and stable on the 8GB VM. Fresh data collection began immediately after the reset and the live attack map confirmed new traffic within minutes of coming back online.
